## 2026-10-19 — fix(hooks): PluginDriftCheck reads the loader's plugin list and rescans mid-session

- `PluginDriftCheck.hook.ts` (#647): every load directory that `claude plugin list --json` reports (`readFromFolder`, else `installPath`) is now scanned for mods beside the static enumeration. This is a union, so a plugin either side misses is still read. A listed skills-dir plugin that is not user scope gets the project origin, which the allowlist never covers. Entries are isolated and sanitized like every other untrusted value. A missing, failing or non-array listing leaves the static scan to run alone. The listing runs once per full scan within a 2.5 s budget. A slower CLI is killed, the static scan stands alone, and the session state is marked incomplete so the next prompt rescans. The listing names no hook modules, so the `modules` check is still the hook's own parse of `hooks.json`, and the parser differential remains for that one file.
- `PluginDriftCheck.hook.ts` (#618): the hook is now also registered on `UserPromptSubmit`. Its cheap path reads this session's state file at `~/.local/state/plugin-drift/SESSION_ID` (plain text, ending in an `end` line so a truncated file reads as damaged) and stats every path the last full scan read or listed, roughly 510 on the operator's machine. It parses no JSON. Only when a size, mtime, inode or existence changed does it run the full mod scan, and then it names only the mods and unverifiable plugins this session has not been told about yet. A missing or damaged state file counts as a change, and so does a change to `CLAUDE_CODE_PLUGIN_DIRS` or `CLAUDE_CONFIG_DIR`. Each `CLAUDE_CODE_PLUGIN_DIRS` folder, its children and their manifests are watched. SessionStart prunes state files older than 30 days. Measured on the operator's machine (524 watched paths): about 33 ms for the cheap path, against a bun startup floor of about 38 ms. A full scan takes about 56 ms without the listing and about 900 ms with it.
- `PluginDriftCheck.hook.ts`: `CLAUDE_CODE_PLUGIN_CACHE_DIR` moves the plugins root (`installed_plugins.json`, `known_marketplaces.json`, `marketplaces/` and `cache/`), and claude.ai synced plugins stay under the config dir, which was checked against the CLI. Each absolute or `~`-prefixed `CLAUDE_CODE_PLUGIN_DIRS` entry is scanned statically as `NAME@inline`. A relative entry is skipped, as the loader skips it, and an archive is reported as unverifiable.
- `PluginDriftCheck.hook.ts`: when `CLAUDE_CONFIG_DIR` is set, the static scan and the drift checks read the plugin registry, cache, settings and skills under it instead of `~/.claude`, as Claude Code does (https://code.claude.com/docs/en/claude-directory).
- `check-hooks-wired.sh`: new `EVENT_WIRING` check. It warns when a hook that needs a specific event is wired only elsewhere. It requires `PluginDriftCheck.hook.ts` on both `SessionStart` (install drift and the full scan) and `UserPromptSubmit` (the rescan). The operator still has to add the `UserPromptSubmit` registration to the private `settings.json`.
- `CLAUDE-GUIDE.md` (Hooks): the mod scan is documented as best-effort, explaining why. Claude Code exposes no list of loaded hook modules and no plugin-reload event.
- `plugin-drift.test.sh`: every case now runs against a stub `claude` on PATH. New cases cover listing-only mods, `readFromFolder` precedence, hostile listing entries, fallback when the CLI fails or prints garbage, and the listing time budget. The rescan cases cover a mod installed or edited in place after SessionStart, no repeated reports, per-session state, damaged state, a cwd change, an unsafe session id, and pruning. Further cases cover a truncated state, a listing that fails and then recovers, a change in the loader environment, a project skills link replaced by a directory, `~` and relative `CLAUDE_CODE_PLUGIN_DIRS` entries, and a moved plugins root.
