## 2026-10-19 — fix(hooks): PluginDriftCheck reads the loader's plugin list and rescans mid-session

- `PluginDriftCheck.hook.ts` (#647): every load directory that `claude plugin list --json` reports (`readFromFolder`, else `installPath`) is now scanned for mods beside the static enumeration. This is a union, so a plugin either side misses is still read. A listed skills-dir plugin that is not user scope gets the project origin, which the allowlist never covers. Entries are isolated and sanitized like every other untrusted value. A missing, failing or non-array listing leaves the static scan to run alone. The listing took about 1 s, so its result is cached in `~/.local/state/plugin-drift/listing.cache` and keyed on the signatures of `installed_plugins.json`, `known_marketplaces.json` and `settings.json`, and the `~/.claude/skills` directory, the working directory, and the `plugin.json` of every listed plugin (whose name is its id). When `CLAUDE_CODE_PLUGIN_DIRS` or `CLAUDE_CONFIG_DIR` is set, the cache is bypassed and the CLI runs on every scan. A failed listing is never cached, and it marks the session state incomplete so the next prompt rescans. Both state files store paths and ids as hex-encoded UTF-16 code units, which handles a lone surrogate without throwing. The listing names no hook modules, so the `modules` check is still the hook's own parse of `hooks.json`, and the parser differential remains for that one file.
- `PluginDriftCheck.hook.ts` (#618): the hook is now also registered on `UserPromptSubmit`. Its cheap path reads this session's state file at `~/.local/state/plugin-drift/<session_id>` (plain text, ending in an `end` line so a truncated file reads as damaged) and stats every path the last full scan read or listed, roughly 510 on the operator's machine. It parses no JSON. Only when a size, mtime, inode or existence changed does it run the full mod scan, and then it names only the mods and unverifiable plugins this session has not been told about yet. A missing or damaged state file counts as a change, and so does a change to `CLAUDE_CODE_PLUGIN_DIRS` or `CLAUDE_CONFIG_DIR`. Each `CLAUDE_CODE_PLUGIN_DIRS` folder, its children and their manifests are watched. SessionStart prunes state files older than 30 days. Measured on the operator's machine: about 34 ms for the cheap path (the bun startup floor is about 35 ms), about 60 ms for a full scan with the listing cached, and about 950 ms when the listing cache misses.
- `PluginDriftCheck.hook.ts`: when `CLAUDE_CONFIG_DIR` is set, the static scan and the drift checks read the plugin registry, cache, settings and skills under it instead of `~/.claude`, as Claude Code does (https://code.claude.com/docs/en/claude-directory).
- `check-hooks-wired.sh`: new `EVENT_WIRING` check. It warns when a hook that needs a specific event is wired only elsewhere. It requires `PluginDriftCheck.hook.ts` on both `SessionStart` (install drift and the full scan) and `UserPromptSubmit` (the rescan). The operator still has to add the `UserPromptSubmit` registration to the private `settings.json`.
- `CLAUDE-GUIDE.md` (Hooks): the mod scan is documented as best-effort, explaining why. Claude Code exposes no list of loaded hook modules and no plugin-reload event.
- `plugin-drift.test.sh`: every case now runs against a stub `claude` on PATH. New cases cover listing-only mods, `readFromFolder` precedence, hostile listing entries, fallback when the CLI fails or prints garbage, and listing-cache reuse and invalidation. The rescan cases cover a mod installed or edited in place after SessionStart, no repeated reports, per-session state, damaged state, a cwd change, an unsafe session id, and pruning. Further cases cover a truncated state or cache, a listing that fails and then recovers, a change in the loader environment, and a project skills link that is replaced by a directory.
